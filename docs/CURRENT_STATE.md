## Shared spans, threads, exploration and moves, S5

The shared core now has named Attention Spans, posts and nested replies, exploration branches with typed distillations, and the demo's thinking moves. They are in `packages/core` (`spans`, `exploration`, `moves`, `sealed`) and sit beside continuity without touching it. Tests try every operation against commitments and NOW, including hostile names, extra fields and forged records, and none of them can change either. Post and reply text is stored exactly and checked against its hash on every read. If words on disk change, the thread shows them with a warning and nothing new is built on them.

The portable format did not change. Posts are captures with `span` and `parentId` in their metadata, and spans, branches, distillations and move revisions are one derived record each. A bundle made before this slice (kept as a test fixture) still verifies and restores on all three adapters, and the new records round trip across every adapter pair. The conformance suite now runs one fixed script of S5 operations on each adapter and requires the same resulting state, and its bad-record refusals include S5-shaped records. See [the export notes](EFFORT_EXPORT.md).

Parity is an executable test: one scripted sequence, including refused steps, runs through the browser demo's own modules and through the shared core, and the resulting spans, posts, branches, distillations and moves must match. The CLI gained `span create`, `span list`, `post`, `reply`, `thread`, `explore`, `distill` and `explorations`, each with a subprocess test. See [CLI usage](../apps/cli/README.md).

Measured: the full suite is 426 tests with 0 skipped on Node 22.23.4. I added mutants for the new controls to `scripts/mutate-check.mjs` but haven't run `check:mutations` on this branch. I did check by hand that the new tests fail when each of those controls is broken, apart from a loop guard that hangs instead of failing, which I left out.

What is not built. Branch statuses (parked, discarded, weird but alive) and evidence marking are not ported. There is no command for editing moves, turning a distillation into a proposal, or attaching a move to a branch, though the core has all three. Explorations in the core don't carry a return point, because those live in continuity. The browser demo doesn't use these modules yet and its behavior is unchanged.

Known gaps. Spans can't be renamed or removed. A second restore keeps the destination's version of any record with the same ID but different content, which for a move revision means two machines that edited the same move won't merge. Reading takes a full store snapshot each time, so large stores will be slow. The checksums catch accidents and ordinary edits, not someone who can recompute them.

## Shared continuity and CLI, S4

The shared core now supports explicit source-quote promotion, one deliberately activated NOW, completion notes labeled as self-reports, retained drop reasons and exact hold/resume packets. Every commitment source is reverified, including inactive and terminal history. Capturing and ranking suggestions never promote work or replace the active commitment. Completing the active item leaves NOW empty until another deliberate selection.

The CLI's former inferred `now` ranking is now `suggest`; `now` shows only an explicitly activated commitment. Existing captures are retained. Use `promote <captureId> <start> <end>`, then `activate <commitmentId>`. See [CLI usage](../apps/cli/README.md) and [core continuity](../packages/core/README.md#continuity).

All three adapters expose atomic derived-record compare-and-swap. File continuity writes are staged and synced before replacement, preserving prior captures if a write fails partway. State checksums detect corruption; the human-authority argument states caller intent and does not authenticate identity. Command IDs make uncertain-write retries idempotent. Consumed return points refuse new resume commands.

Deterministic interruption budgets protect chosen work, respect dismissals and quiet hours, and suppress duplicate keys. Advisory night friction always leaves capture, journaling and tomorrow's first step available. Seeded lifecycle and policy tests cover these rules. The browser demo and phone app keep their existing implementation in this slice.

### Known gaps

When an original fails its hash and a commitment was made from it, the continuity commands (`now`, `activate`, `complete`, `drop`) stop on purpose, and I don't yet have a command to set the damaged record aside. `list` and `suggest` now warn about the damaged item and `suggest` skips it, and `effort export` keeps the damaged record whole in the backup's quarantine section, so nothing you wrote is lost. But restoring that backup into a fresh store does not unstick things: the commitment comes along, still points at the damaged original, and the same commands still stop. Capturing, `list`, `suggest`, `verify` and `export` keep working. A damaged original that no commitment points to doesn't block continuity.

## Earlier proposal release: derived preparation and explicit choice

A person should be able to carry a newly distilled idea forward, preserving exactly where it came from. Preparing a proposal must not create a commitment; choosing an exact detail is a second explicit action.

The persistence and public controls are released:

- **Consider as a next step…** prepares exact derived writing and opens its organized original view. It leaves NOW unchanged; a second explicit **Make this my next step** action commits an exact source range. Verified lineage is readable in the reply and original dialog, with an honest recovery state when unavailable. See `docs/PROPOSALS.md`.
- `createStore().prepareProposal({distillationId}, {expectedEpoch})` creates an ordinary reply capture with the distillation's exact text, its source as parent, and a deterministic workspace-scoped ID. It leaves NOW and commitment history unchanged.
- `derivedFromId` points to the distillation. `derivedHash` seals every proposal field except itself; the existing hash continues to verify exact text.
- Unhinged branches refuse preparation. Repeated/concurrent requests reuse the same proposal. Readback failure can be retried without duplication. Reset epochs fence stale forms.
- `validateProposalProvenance` returns `verified`, `recovery`, or null for an ordinary capture. It verifies text, source, span and non-sandbox lineage. Missing or damaged lineage must be visibly distinguished from verified provenance.
- Capture validation accepts only the exact proposal shape. At that release, browser backup was version **7**, accepting versions 1 through 6. IndexedDB was schema 5; no new tables were needed.
- Read recovery preserves intact proposal text while recording damaged provenance separately. Metadata checksum failure preserves the whole raw capture through the existing quarantine path.
