# From an idea to a chosen step

A distillation can contain an idea that wasn't in the original capture. Choosing only from the old source would lose that new thinking. Automatically turning the distillation into work would violate the product's central boundary: captured does not mean owed.

The proposal flow keeps both sides of that boundary. **Consider as a next step…** prepares the distillation's exact text as a new, linked reply. It opens an organized view of that new original, without changing NOW or creating commitment history. A second, explicit **Make this my next step** action selects an exact quote and records the existing commitment transition. **Choose from original…** remains available when the person prefers the earlier thought instead.

Proposal lineage is readable from the reply and original view. It preserves the distillation, exploration, dial and original source. All of these are the person's own writing; checksums verify stored bytes and links, not factual truth. Done actions remain separately self-reported.

## Authority and retry behavior

An unhinged branch can't prepare a proposal. A person can explicitly create a child with another dial, then distill that child before considering action. The dial does not invoke a model or grant external authority.

Each distillation reuses its saved proposal, including after backup restoration into a new workspace. Concurrent preparation or a failure after the database commits doesn't create another copy. Workspace epochs fence delayed actions after a reset. A changed source during verification refuses preparation instead of reporting a fresh verified relationship.

Preparing a proposal while someone navigates away doesn't pull them back into the old view. A workspace reset prevents its old asynchronous action from opening a stale proposal dialog. An app update waits for pending preparation to finish, just as it waits for draft saving.

## Storage and recovery

Proposal captures carry the original text hash, a distillation ID and an additional hash over the full proposal metadata. The capture is a reply to the exploration's source in the same Attention Span. The original distillation and branch remain separate immutable records.

Browser backup 7 includes proposal captures and derivation links, and accepts backups 1 through 6. Restoring adds missing records and refuses conflicting IDs. A proposal whose derivation is damaged retains its own exact writing with an explicit source-recovery label. Damaged proposal metadata is preserved through the raw quarantine path. Neither case silently claims verified lineage.

## Verification

The proposal tests exercise exact text, inert preparation, separate quote selection, sandbox refusal, concurrent retries, accepted-save readback failure, source changes during verification, resets during hashing, backup round trips across epochs and damaged lineage. The browser suite exercises the public controls, keyboard flow, phone layouts, fault injection, multi-tab state, backup upgrades, recovery labels and offline reopening.

This is a browser workspace feature. It doesn't execute a proposal, call a provider, send a message or touch the private Android app.
